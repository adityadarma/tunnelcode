# Overview

TunnelCode is an application that lets an AI Coding Agent run locally on the user machine while all interaction happens through the browser.

This project is inspired by OpenCode, but the UI is split out into a web app so the user can control the agent from anywhere as long as the device is online.

TunnelCode is not an IDE.

TunnelCode is not an AI Provider.

TunnelCode is a bridge between Browser, Server and Local AI Agent.

---

# Project Goals

The MVP must be able to:

- run an AI Agent locally
- pair using a QR Code
- let the browser hold a conversation
- let the browser receive AI streaming responses
- let the browser reconnect without losing chat
- store conversations in the database
- keep the engine interchangeable

# Pairing Approval

After the browser sends the code, pairing is not complete yet.

The server creates a 4 digit approval number.

The browser shows that number.

The CLI shows the same number and waits for the user to approve.

The user approves in the terminal with a single keypress.

Approval rules

The approval number is generated by the server.

The approval number never travels in a URL.

The number shown in the browser must match the number shown in the terminal.

Only the CLI can approve.

A rejected or ignored request never pairs.

Reason

The code travels in a query string, so it can leak into browser history,
referer headers, and access logs.

The approval number is not in the URL, so a leaked URL alone cannot pair.

Every pairing attempt becomes visible in the terminal, so an attempt by
somebody else can be rejected.

---

# Pairing Limits

The pair endpoint is rate limited.

A wrong code counts against the limit.

Reason

The code is short enough to be worth guessing if guessing were free.

---

# Pairing Code Lifetime

The code is valid while the CLI session is running.

The code can only be used once.

Once used, the code cannot be used again.

Idle Timeout

1 hour without conversation.

Activity that resets the timer:

Message from user

Message from assistant

Activity that does not reset the timer:

WebSocket heartbeat

Browser connect

Browser reconnect

Reason

Heartbeat keeps running while the browser is open.

If heartbeat counted as activity, the timeout would never be reached.

After the idle timeout:

CLI exits

Session ends

The code cannot be used again

A new pairing requires a new code.

# Browser

The browser acts only as UI.

The browser never touches the filesystem.

The browser never runs AI.

All requests are sent over WebSocket.

---

# Runtime

Realtime state is kept in memory.

The database is only for persistence.

Do not use the database as a realtime transport.

---

# Conversation

Every conversation must be stored.

A conversation records the engine it runs on and the model it asks for.

AI streaming is not stored as it arrives.

Buffer all deltas.

Once the assistant finishes, store it as a single message.

A browser refresh must be able to load the full history.

---

# Engine

Use the Adapter Pattern.

First engine:

OpenCode

The interface must allow implementing:

Claude Code

Gemini CLI

Custom Engine

Without changing business logic.

Engine Selection

The CLI offers the engines that are both supported here and installed on the
machine. Nothing else is offered.

A CLI with no installed engine does not start a session.

The browser chooses the engine when it creates a conversation.

A conversation keeps that engine for life. It cannot be changed.

The model can be changed at any time, within the conversation's engine.

The engine named in Setup is what a new conversation starts on.

See ADR-020.
